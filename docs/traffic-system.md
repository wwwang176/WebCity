# 交通系統 (Traffic System)

WebCity 的交通系統模擬車輛在車道級別的移動，包含通勤、貨運和服務車輛。

---

## 車輛 (Vehicle)

### 車輛屬性

| 屬性 | 說明 |
|------|------|
| `id` | 唯一識別碼 |
| `length` | 車體長度（世界座標） |
| `width` | 車體寬度（世界座標） |
| `lane` | 所在車道（0-based） |
| `edgePath` | 路徑邊列表 |
| `edgeIndex` | 當前邊索引 |
| `edgeProgress` | 當前邊上的行進距離 |
| `speedMultiplier` | 隨機速度因子 (0.8~1.0) |
| `stallTime` | 停滯累計時間（秒），超過 10 秒則強制消失 |
| `arrived` | 是否已到達目的地 |

### 車輛類型

根據車體長度分類：

| 長度 | 類型 | 權重 |
|------|------|------|
| ≥ 0.58 | bus (公車) | - |
| ≥ 0.35 | truck (卡車) | 10% |
| ≥ 0.24 | van (貨車) | 15% |
| < 0.24 | car (轎車) | 75% |

### 服務車輛

| 類型 | 長度 | 寬度 |
|------|------|------|
| police (警車) | 0.22 | 0.09 |
| fire (消防車) | 0.55 | 0.125 |
| health (救護車) | 0.30 | 0.10 |
| garbage (垃圾車) | 0.45 | 0.125 |

## 車道圖 (LaneGraph)

### 概念

LaneGraph 將格子級的道路網路轉換為車道級的連線圖，支援精確的車輛移動模擬。

### 組成

- **ConnectionPoint（連接點）**: 每個道路格子的每條車道在每個方向都有 entry（進入）和 exit（出發）點
- **LaneEdge（車道邊）**: 連接兩個 ConnectionPoint 的路段

### 邊類型

| 類型 | 說明 |
|------|------|
| `straight` | 直行路段 |
| `turn` | 轉彎路段（使用 Bezier 曲線） |
| `lane_change` | 換道路段 |
| `merge` | 合流路段 |

### 車道寬度

每條車道的橫向偏移: `LANE_WIDTH = 0.18` 格

### 路口判定

roadFlags 中有 3 個以上方向旗標的格子為路口（intersection）。路口內的格子是「透明的」，不產生自己的連接點。

---

## 車道邊的曲線幾何

### Bezier 曲線

車道邊的轉彎路段使用**二次 Bezier 曲線**（quadratic Bezier）表示：
- 起點: `edge.from.position`
- 控制點: `edge.bezierControl[0]`
- 終點: `edge.to.position`

直行路段使用線性插值。

控制點的計算使用進入和離開方向的切線交點，產生近似 90° 圓弧的曲線。

### 弧長查找表

三次 Bezier 曲線使用弧長查找表（arc-length LUT）進行等速插值，通過二分搜尋將距離映射到參數 t。

## 車輛移動

### 基礎速度

```
邊速度 = EDGE_SPEED × (道路速限 / REFERENCE_LIMIT) × speedMultiplier × 壅塞速度倍率
```

- `EDGE_SPEED` = 7 世界單位/秒
- `REFERENCE_LIMIT` = 50（速限 50 = 1.0 倍速）

### 漸進加減速

車輛不再瞬間改變速度，而是根據加減速率漸進調整：

| 參數 | 值 | 說明 |
|------|-----|------|
| `ACCEL` | 8.0 | 加速率（世界單位/秒²） |
| `DECEL` | 12.0 | 減速率（世界單位/秒²） |
| `BRAKE_DISTANCE` | 1.5 | 煞車區距離 |

三階段速度控制：
1. **加速**: targetSpeed > currentSpeed → 以 ACCEL 率加速
2. **安全煞車**: 前方障礙 < BRAKE_DISTANCE → 距離比例降速（snap braking）
3. **漸進減速**: 進入低速限路段 → 以 DECEL 率減速

車輛會**前瞻 2 條邊**偵測速限變化，提前開始減速。

### 前方碰撞偵測

車輛在前方 5 個世界單位 (`LOOKAHEAD_DISTANCE`) 內進行三層碰撞檢查：

#### 1. 同邊前車偵測 (findGapAhead)

在同一邊路徑（`edgePath`）上搜尋前方最近的車輛：
```
gap = 前車進度 - 我的進度 - 我的半長 - 前車半長
```
搜尋跨越多條邊，直到超過前視距離。

**提前收工**:找到一台之後,只有**比它更長**的車才可能在更遠的地方留下更小的空隙
（空隙扣的是兩台車的半個車身,公車比小客車長兩倍多）。所以走完一條邊之後,若

```
gap ≤ 已走距離 - 我的半長 - 這一幀路上最長車身的一半
```

就停止搜尋。那個「最長車身」是每幀在建逐邊索引時實算的,不是照車身表寫死的常數 ——
`Vehicle.length` 與 `traffic.vehicles` 都是公開可改的,寫死等於一條沒有東西強制得了的前提。

12 288 人的存檔實測:每台車每幀走過的邊 10.3 → 2.7。

#### 2. 紅燈偵測 (findRedLightDistance)

檢查前方是否有紅燈。車輛在停止線偏移 0.25 格處停下。

#### 3. 跨邊 AABB 碰撞 (findCrossEdgeGap)

偵測不同車道邊上但物理位置接近的車輛。

車輛每幀照**終點連接點**（`edge.to.id`）分組（`mergeGroups`），查詢只走同一組 ——
這段程式唯一在意的關係就是「會不會匯進同一個點」,那是查得出來的分組,不是空間問題。

- **檢查半徑**: 2.0 世界單位（在迴圈裡算距離,太遠的不算擋路）
- **AABB 縮放**: 1.1（10% 安全邊距）

> 原本是用逐格的空間雜湊撈半徑 2.0 內的所有車再一台一台丟掉。12 393 人的存檔實測,
> 撈回來的九成以上第一個條件就被刷掉:每 tick 檢查 301 783 台 → 分組後 27 459 台。

跨邊碰撞只在**合流兄弟邊**（目的地相同的連接點）之間發生。優先級規則：
- `progressRatio` 更高（更接近合流點）→ 優先通過
- 相同 progressRatio → 較低 ID 優先

碰撞判定使用方向投影：
```
前向距離 = 相對位置投影到我的前進方向
橫向距離 = 相對位置投影到我的垂直方向
若 橫向距離 ≤ (我的半寬 + 對方半寬) × 1.1
  → gap = 前向距離 - (我的半長 + 對方半長) × 1.1
```

### 停滯消失

車輛停滯超過 10 秒 → 強制消失。停滯偵測使用 `intendedMove`（預期移動量）而非實際位移，更準確判斷車輛是否真正卡住。初始有 0~5 秒的隨機抖動。

### 公車特殊行為

公車到站時會停靠 2 秒（`BUS_DWELL_SECONDS`），期間不移動。

## 壅塞 (Congestion)

**檔案**: `src/core/traffic/RouteCongestion.ts`

壅塞是從**需求**算出來的,不是數畫面上有幾台車。路上的車輛實體有數量上限
（`VEHICLE_CAP_MAX`）、會被生成點檢查擋掉,那是演繹;真正的依據是
[CongestionFlowPredictor](#congestionflowpredictor壅塞流量預測) 產生的逐格流量圖:
**每一格上有多少人的通勤路線經過,除以那一格的車道數**。

### 一格有多擠

```
負載 = 逐格流量 / FLOW_PER_LANE_SATURATED   (9000)
擁擠度 = min(1, 負載 ^ CONGESTION_EXPONENT)  (指數 4)
```

指數不是 1。空的路上多一台車沒感覺,快滿的路上多一台車整條隊伍卡住 —— 線性會把這兩件事
當成一樣重,結果玩家花錢打通一個快爆的路口,回饋跟拓寬一條本來就順的路差不多。

四次方是交通工程的 BPR 函數常用的形狀,但**參數不是工程值**:BPR 在滿載時只多 15%
的行駛時間,這裡是 ×2;而且這裡的「流量」沒有時間單位,是「多少人的路線經過」。
兩個常數都是遊戲平衡的旋鈕,照 12 280 人的參考城市校準。

### 這一趟有多擠

```
routeCongestion = 沿途每一格擁擠度的平均
```

取平均而不是「最塞的那一格」:開車時間是沿路累積的,卡一個路口跟整條路都在爬不是同一
件事。瓶頸會主導這趟通勤,但那是因為快滿的格子代價暴增（指數 4）,不是因為取最大值。

路線來自 `CommuteCache` —— **是這個人自己走的那條路**,不是全城共用一個數字。逐路線的
結果會快取,流量圖每 60 tick 重算時整個清掉。

### 全城平均

問不到某一趟的路線時的退路,也給公車用（[壅塞對公車的影響](transport-system.md#壅塞對公車的影響)）。

```
cityCongestion = 所有格子擁擠度加總 / 全城道路格數
```

分母是**全城道路格數**,空路也算進去 —— 那才是「蓋了路有沒有用」反映得出來的地方。

### 用在哪

| 用途 | 讀哪一個 |
|------|---------|
| 運具選擇（開車 vs 大眾運輸） | `congestionFor(from, to)` 逐路線 |
| 公車速度 | 全城平均 |
| 地圖圖層與面板的壅塞排行 | 逐格流量原始值 |

> **歷史**: 這裡原本是 `車輛數 / 容量`,而且分母只算「現在有車的格子」。實測 12 254 人的
> 存檔連續取樣六次全部是 1.000 —— 城市一有規模就永遠貼在上限,蓋路不會降、塞車不會升
> （BUG-326）。`src/core/traffic/Congestion.ts` 是那個舊模型留下的模組,目前沒有任何
> 生產端程式碼引用它。

## 紅綠燈 (Traffic Lights)

### 放置規則

只有在 **兩條主要道路** (FOUR_LANE 或 SIX_LANE) **同時在南北和東西兩個軸向交叉**的路口才會設置紅綠燈。

### 相位

| 相位 | 南北 | 東西 |
|------|------|------|
| 0 | 綠燈 | 紅燈 |
| clearing | 全紅（淨空） | 全紅（淨空） |
| 1 | 紅燈 | 綠燈 |
| clearing | 全紅（淨空） | 全紅（淨空） |

### 相位時間

- 3 方向路口: 4 秒
- 4 方向路口: 8 秒

### 全紅淨空相位 (All-Red Clearance)

每次相位切換之間插入 1 秒的全紅淨空期（`CLEARANCE_DURATION = 1`）。淨空期間：
- 所有方向均為紅燈
- 車輛和行人均不可通過
- 渲染器顯示全紅燈號

相位開始時有基於位置的隨機偏移，避免所有紅綠燈同步。

### 行人過馬路判定

行人只在**進入路口時**檢查紅綠燈，已在路口內的行人不再重複檢查。斑馬線邊記錄所屬的 `intersectionCellKey`，確保查詢正確路口的燈號。

## 貨運系統 (FreightSystem)

### 運作流程

每 tick：
1. 工業建築產生貨物（每棟 2 單位/tick）
2. 商業建築消耗貨物（每棟 1 單位/tick）
3. 產生的貨物進入倉儲
4. 消耗量從倉儲扣除
5. 不足的部分為缺貨量

### 外部貨物來源

- **鐵路貨運**: 每列貨運火車 +10 貨物/tick
- **機場貨運**: 消耗機場的貨物配額
- **鐵路外部連接**: 連接地圖邊緣的鐵路可帶入外部貨物

### 缺貨影響

缺貨比例 = 缺貨量 / 消耗量（0~1）。缺貨會影響商業區的成長。

## 車輛上限

```
上限 = min(2000, 20 + 人口 × 0.3)
```

這個上限管的是**畫面上同時能跑幾台**,超過就會卡。過境車流與貨運一樣佔路,所以計數看的是
**全部車輛**,不是只看通勤車。面板上那張「有多少居民在開車」的卡片問的是另一件事,走
`getCommuteVehicleCount()`。

## 生成點檢查

車輛都放在 `edgePath[0]` 的起點、進度 0。而通勤路線是共用的（路線池把同一個陣列交給每個
走這條路的人）,所以同一條路上同時出發的人會全部疊在同一個點上 —— 畫面上是一坨,而且路口
回堵時會卡在那裡不動。

生成前先看那個位置有沒有車,有就這一趟不出門,讓那個人下次再試（`spawnVehicleOnEdges`）。
**公車不受這道檢查影響** —— 公車少一台是修不回來的,`busVehicleIds` 與 `route.vehicles`
仍然算著它,沒有東西會去對帳（BUG-115）。

### 多近算被佔著

```
SPAWN_CLEARANCE.ALONG  = 0.3   前後（沿行進方向）
SPAWN_CLEARANCE.ACROSS = 0.10  左右
```

兩個方向分開量,而且**不看佔位那台車實際多長多寬** —— 差別在畫面上看不出來。兩個數字都有
上下界（測試裡有斷言）：

- `ALONG` 要比最長的車身長（0.26）,否則兩台車中心只差半個車身也會各自生成,就是穿模
- `ACROSS` 要比最窄的車道間距小。最窄的是單行道兩車道:`0.55 / 2 / 2 = 0.1375`。比它大的話
  隔壁車道永遠有車擋著,路上的車會少一大截

這兩條界線之間塞不下一個「單一半徑」——車身 0.26 就已經比車道間距 0.1375 寬了,所以是兩個
數字而不是一個。

### 逐格索引

檢查只問生成點附近那幾格（`spawnHash`,格大小 1.0）。索引跟 `cellDensity` 同一個生命週期:
每幀在**清掉抵達的車之後**重建,新車生成時當場補一筆 —— 同一個 tick 裡接著出門的人才看得到它。

沒有共用跟車那一份格點資料:那一份在每幀處理**開始時**就建好,到了清車之後還留著已經抵達的
車,而生成點正好就是別人的目的地。

> 原本每要放一台車就掃過路上**所有**車。12 334 人的存檔實測:每 tick 約 394 次生成嘗試
> × 890 台車 ≈ 35 萬次距離計算,**49ms/tick**（速度 1 的一個 tick 只有 250ms）。改成逐格
> 索引之後 2.1ms/tick（BUG-323）。

## 每幀的處理順序

車輛由前往後處理（沿自己路徑走得愈遠的愈先），而且每台車走完之後會把自己的新位置與
「有沒有在減速」寫回逐邊索引。所以**後車讀到的是前車這一幀剛算好的狀態**,不是上一幀的。

這件事有實測:同一份存檔跑一幀,把排序反過來,842 台車有 547 台的位置與速度會不一樣。

排序鍵（沿路徑走了多遠）寫在車輛物件上,不是放在 Map 裡 —— 871 台車的排序約 8 500 次比較,
每次比較查兩次 Map 就是一幀上萬次雜湊查詢。

鍵本身走 `PathLengthCache`:前綴長度和只跟**路徑**有關,跟哪台車無關,而通勤路線是共用的,
所以走同一條路的幾百台車共用同一份（`WeakMap`,以路徑陣列為 key,路線被淘汰時跟著回收）。
實測每幀為了排序掃過的邊:14 438 → 22。

## 通勤系統

### 通勤流程

每個通勤市民（工作年齡、有住所和工作場所）按以下流程決定交通方式（模式選擇演算法詳見[大眾運輸 — 交通模式選擇](transport-system.md#交通模式選擇-mode-choice)）：

```
1. chooseMode() 決定交通模式
   ├─ WALK (距離 ≤ 3) → 不產生車輛，加入行人池
   ├─ BUS/METRO/RAIL/FERRY → 不產生車輛
   │   ├─ 加入最近站點的 dailyRiders
   │   ├─ 產生 FIRST_MILE 行人行程（住所→站點）
   │   └─ 產生 LAST_MILE 行人行程（站點→目的地）
   └─ DRIVE → 產生通勤車輛
       ├─ 檢查快取路徑
       ├─ 無快取 → findRoadPath + refineLanePathVariants
       ├─ 隨機選擇車道變體（分散到不同車道）
       └─ 儲存到 CommuteCache
```

### 通勤時段

| 時段 | 方向 | 車輛產生 | 行人密度倍率 |
|------|------|---------|-------------|
| 早高峰 (6~9) | 住所→工作 | 最大 | 1.0 |
| 午間 (10~16) | 隨機商業交通 | 少量 | 0.3 |
| 晚高峰 (17~21) | 工作→住所 | 最大 | 1.0 |
| 夜間 (22~5) | 無 | 無 | 0.05 |

### 每 tick 產生數量

```
maxPerTick = max(5, ceil(合格通勤者數 / 4))
```

4 ticks 的高峰期內要把所有通勤者都發出去。

### 通勤快取 (CommuteCache)

儲存市民的通勤路徑（LaneEdge 序列），避免每次重新計算。

- **路線共享**: 相同起訖點的市民共享預計算的 LaneEdge 路徑變體
- **路線變體**: `refineLanePathVariants` 為每個起訖點計算多條車道變體
- **格子索引**: 每個路徑記錄通過的格子，道路變更時只失效受影響的路線
- **世代機制**: `roadGeneration` 遞增標記路網變更，舊世代的快取自動失效
- **失敗快取**: 無路徑的起訖點也記錄為 `failed`，避免重複搜尋
- **延遲重算**: 失效路線在下次使用時才重新計算（不一次全部重算）

### 道路切斷的即時處理

當道路被拆除時，立即檢查所有在職市民的工作場所是否仍可達：
- 不可達 → 立即失業（`workplaceId = null`）
- 不等到 jobRelocationTick（避免市民在空中的車輛消失）

## 行人系統 (Pedestrian System)

### 行人代理 (PedestrianAgent)

每個行人是獨立的代理，在人行道圖上移動。

| 屬性 | 說明 |
|------|------|
| `citizenId` | 對應的市民 ID |
| `tripType` | 行程類型 |
| `edgePath` | 人行道邊路徑 |
| `state` | 當前狀態 |
| `speedMultiplier` | 個人速度倍率 (0.5~1.0) |
| `offsetX` / `offsetZ` | 固定世界空間偏移（視覺效果，避免旋轉時漂移） |
| `age` | 已存活秒數（超過 120 秒消失） |

### 行程類型

| 類型 | 說明 |
|------|------|
| `FULL_WALK` | 完整步行通勤 |
| `FIRST_MILE` | 第一哩（住所到大眾運輸站） |
| `LAST_MILE` | 最後一哩（大眾運輸站到目的地） |
| `DECORATIVE` | 裝飾性行人（隨機出現在人行道上） |

### 行人狀態

| 狀態 | 說明 |
|------|------|
| `WALKING` | 行走中 |
| `WAITING_SIGNAL` | 等紅綠燈 |
| `WAITING_CROSSING` | 等待過馬路 |
| `ARRIVED` | 已到達目的地 |

### 行人數量限制

```
上限 = clamp(人口 × 5%, 50, 2000)
```

裝飾性行人最多佔 15%。

### 行人速度

基礎速度: 0.375 世界單位/秒（`PEDESTRIAN.SPEED`）

### 行人生成位置

行人從建築的**門節點 (door node)** 生成，而非路徑上的隨機位置。這確保行人始終從建築入口出發。

### 行人尋路

使用**多目標 A***（multi-target A*）進行建築感知尋路：
- 起點為出發建築的門節點
- 終點為目標建築的門節點集合（任一到達即結束）
- 路徑快取上限: 2000 條

## 人行道圖 (SidewalkGraph)

### 節點類型

| 類型 | 說明 |
|------|------|
| `sidewalk` | 人行道節點 |
| `building_entrance` | 建築入口（門節點） |
| `building_corner` | 建築角落節點 |

站牌沒有自己的節點類型：它在圖裡就是一棟 1×1 建築，四個門節點靠 `building_access`
接上路邊。

### 邊類型

| 類型 | 說明 |
|------|------|
| `sidewalk` | 人行道段 |
| `crosswalk` | 斑馬線（過馬路） |
| `level_crossing` | 平交道穿越 |
| `building_access` | 建築出入口通道 |
| `building_wall` | 建築牆面步道 |

### 過馬路只能走路口

斑馬線只在連通方向 ≥ 3 的路口周邊產生。直路段與轉角都沒有，所以**一條馬路的兩側
在圖上是兩條不相連的平行線** —— 要到對面，得走到最近的路口、過去、再走回來。

這是設計，不是缺漏。它的代價是繞路的距離完全由路口間距決定：間距 8 格時，正對面
那一格實際要走 7.44 格；間距 20 格要走 19.44 格；一條完全沒有岔路的直路則永遠走
不到對面。

因此「站牌蓋在哪」是一個有後果的決定：蓋在路段中間只服務得到同一側，蓋在路口旁邊
兩側都涵蓋得到。

### 建築周邊步道 (Building Perimeter Walkway)

每棟建築在人行道圖中生成 8 個節點：

- **4 個門節點** (bN, bS, bW, bE): 位於建築各面中央，距離中心 `DOOR_NODE_DIST ≈ 0.41`
- **4 個角落節點** (bNW, bNE, bSW, bSE): 位於建築四角，距離中心 `CORNER_NODE_DIST`（略大於門節點）

連接規則：
- 門節點連接到最近的道路人行道節點（`building_access` 邊）
- 角落節點連接到最近的道路人行道節點
- 相鄰建築之間的角落節點互相連接
- 門節點與角落節點之間以 `building_wall` 邊連接

此結構使行人可以沿建築外牆行走，並從建築門口進出。

### 人行道生成規則

- 人行道節點沿道路邊緣生成（無相鄰道路的那一側）
- 人行道寬度: 0.14 世界單位
- 斑馬線連接路口兩側的等候點
- 角落節點向外推出，形成**三角形邊結構**（每個面一組三角形）

## LaneGraphPathfinder（車道級 A* 尋路）

取代舊有的兩階段尋路系統（格子級 A* + `refineLanePathVariants`），改為**單階段車道級 A***。直接在 LaneGraph 的 LaneEdge 上搜尋，不再依賴格子級啟發式或路口透明處理，回傳的 `LaneEdge[]` 可直接供 TrafficSimulation 使用。

**檔案**: `src/core/traffic/LaneGraphPathfinder.ts`

### 核心函式

#### `findLanePath(graph, lookup, from, to)`

從建築位置 `from` 到 `to` 找出一條車道級最短路徑。內部呼叫 `laneAStar`，回傳 `LaneEdge[] | null`。

#### `findLanePathVariants(graph, lookup, from, to, count?)`

為同一起訖點產生**多條車道變體**（預設 `VARIANT_COUNT = 3`），使通勤車輛分散到不同車道。使用**懲罰方法（penalty method）**：

1. 第 1 條路徑以零懲罰跑 A*
2. 將已使用的 cell+lane 組合施加 `VARIANT_PENALTY = 3` 倍成本
3. 再跑 A*，找出偏好不同車道的路徑
4. 重複直到產生 `count` 條變體或無法再找到新路徑

起點與終點的格子不計入懲罰（所有變體可共用同一車道進出）。

### 多源/多目標 A*

`laneAStar` 支援多個起點（multi-source）和多個目標（multi-target）：

- **起點**: 呼叫 `findNearbyExitPoints` 收集出發建築及其 Chebyshev `ZONE_ROAD_REACH`（5×5 方框）內所有道路 cell 的 exit ConnectionPoint，全部以 g=0 加入 open list
- **終點**: 呼叫 `findNearbyEntryPoints` 收集目標建築同樣範圍內所有 entry ConnectionPoint，任一被到達即結束
- 透過 `UnifiedRoadLookup.getAllKeysAtPosition()` 支援高架道路（elevation）

> 掃描範圍與 [zone-system](zone-system.md#基本限制) 的內圈放置規則一致：住宅／工作場所可能位於距離道路 2 格的內圈，只掃 4 鄰居會找不到起終點 → A* 沒有 seed → 通勤失敗。Chebyshev 2 保證所有合法放置的建築都能產生車道路徑。詳見 [grid-system — `ZONE_ROAD_REACH`](grid-system.md#共享常數-zone_road_reach)。

### 成本函式

```
cost(edge) = edge.length / (laneSpeedMultiplier(lane) × speedLimit / REFERENCE_SPEED_LIMIT)
```

- `REFERENCE_SPEED_LIMIT = 50`（速限 50 km/h 為 1.0 倍基準）
- 速限越高的道路成本越低，A* 自然偏好快速道路

### 啟發式

```
h(node) = manhattanDistance(node.position, endPos) × 0.01
```

使用極小的啟發式權重（0.01）確保可容許性（admissible），同時仍提供方向性引導。

### 搜尋上限

`maxSteps = 8000`，超過則回傳 `null`（無路徑）。

## CongestionFlowPredictor（壅塞流量預測）

預測各道路格子的通勤流量。採用**雙策略**架構：當通勤快取覆蓋率足夠時使用快速的快取掃描，不足時改用蒙地卡羅抽樣。

輸出的流量圖是**全遊戲壅塞的唯一資料來源**：

| 用途 | 怎麼用 |
|------|-------|
| 運具選擇（開車 vs 大眾運輸） | 沿市民自己的路線逐格平均，見[壅塞](#壅塞-congestion) |
| 公車速度 | 全城平均 |
| 壅塞熱度圖、面板的壅塞排行 | 逐格原始值 |

它跟畫面上生成了幾台車無關 —— 車輛實體有數量上限、會被生成點檢查擋掉，那是演繹。

**檔案**: `src/core/traffic/CongestionFlowPredictor.ts`

### 策略一：`computeCongestionFlow`（快取路線掃描）

從 `CommuteCache` 的 `routeIndex` 直接掃描已快取的通勤路線，零 A* 計算。

**流程**:
1. 透過 `commuteCache.forEachRouteWithRefCount()` 遍歷所有快取路線
2. 每條路線的 `refCount`（共用該路線的市民數）加總到 `totalRefCount`
3. 呼叫 `collectEdgeCells` 取得路線經過的所有格子
4. 將 `refCount` 累加至各格子的流量值
5. **按車道數正規化**: 多車道道路的流量除以 `getLaneCount(cellKey)`

**回傳**: `{ flowMap: Map<string, number>, totalRefCount: number }`

複雜度: O(路線數 × 平均路徑長度)，無需重新尋路。

### 策略二：`computeCongestionFlowMonteCarlo`（蒙地卡羅取樣）

當快取覆蓋率太低（`totalRefCount` 遠小於通勤人口）時使用此備用策略。

**流程**:
1. 呼叫 `buildODPools(deps.citizens, deps.parsePosKey)` 建立出發地（residential）與目的地（destinations）的加權池
2. 決定取樣數: `clamp(totalResWeight / sampleDivisor, sampleCountMin, sampleCountMax)`
3. 每次取樣:
   - 以 `pickWeighted` 隨機選取起點與終點
   - 跳過同一格子或曼哈頓距離 ≤ `MANHATTAN_DISTANCE_THRESHOLD`（3 格）的 OD 對
   - 透過 `deps.chooseTransportMode` 判斷交通模式，僅 `DRIVE` 繼續
   - 呼叫 `deps.findLanePath` 執行 A* 尋路
   - 路徑經過的每個格子流量 +1
4. **按比例放大**: `scaleFactor = totalResWeight / sampleCount`，將取樣流量乘以此因子以推估實際通勤量

**依賴注入**: 透過 `CongestionFlowDeps` 介面注入所有外部依賴（citizens、findLanePath、chooseTransportMode 等），遵循 DIP 原則。

## HighwayConnection（高速公路外部連線）

偵測地圖邊界上的高速公路，建立與外部世界的連線，產生外部人口與貨物流入/流出。

**檔案**: `src/core/traffic/HighwayConnection.ts`

### 邊界掃描邏輯

`updateExternalConnection(mapWidth, mapHeight, grid)` 每 60 tick 由 SimulationLoop 呼叫：

1. 掃描地圖四邊（上、下、左、右）的所有邊界格子
2. 對每個格子檢查:
   - **地面層**: `grid.getCell(x, y)` 的 `roadType === HIGHWAY`
   - **高架層**: 透過 `ElevationManager.get(x, y, level)` 檢查 `MIN_ELEVATION_LEVEL` 到 `MAX_ELEVATION_LEVEL` 的所有層級
3. 使用 `hasInwardFlag(x, y, mapWidth, mapHeight, roadFlags)` 確認道路方向朝地圖**內部**（非平行於邊界）
4. 符合條件的格子加入 `edgeHighwayCells`

### 方向判定（EdgeUtils）

`hasInwardFlag` 定義於 `src/core/grid/EdgeUtils.ts`：

| 邊界位置 | 向內方向 |
|----------|---------|
| 北邊 (y=0) | SOUTH (0b0010) |
| 南邊 (y=max) | NORTH (0b0001) |
| 西邊 (x=0) | EAST (0b1000) |
| 東邊 (x=max) | WEST (0b0100) |

角落格子同時屬於兩條邊界，任一方向符合即可。

### `extractOutOfBoundsEdge`（拖曳超出邊界建路）

同樣位於 `EdgeUtils.ts`。當玩家拖曳道路建設路徑超出地圖邊界時：

- 偵測路徑最後一個點是否在地圖外
- 計算從前一個點到最後一個點的方向，回傳 `outwardFlag`（出向方向旗標）
- 回傳 `truncatedLength`（截斷後的有效路徑長度）

### 常數（`HIGHWAY_EXTERNAL`）

| 常數 | 值 | 說明 |
|------|-----|------|
| `THROUGHPUT_PER_CONNECTION` | 30 | 每個邊界連接點的吞吐量 |
| `SPAWN_PER_100_POP` | 1 | 每 100 人口產生的外部車輛數 |
| `MAX_PER_TICK` | 3 | 每 tick 最大產生外部車輛數 |
| `CAP_RATIO` | 0.9 | 容量上限比率 |

### 外部資源產出

當存在至少一個邊界高速公路連接時，根據連接數量 `count` 計算：

| 資源 | 公式 |
|------|------|
| `populationIn` | max(1, count × 3) |
| `goodsIn` | max(1, count × 8) |
| `goodsOut` | max(1, count × 5) |

### 序列化

支援 `toJSON()` / `fromJSON()` 存檔與讀檔。
