# 建築模型多樣性 — 設計規格

**日期**：2026-08-09
**分支**：`feat/building-model-variety`
**狀態**：設計已確認，待排實作計畫

---

## 1. 背景與問題

玩家回饋：住宅區建築的玻璃反射效果很好，但**建築的樣子太重複**，商業區與工業區也一樣。

進一步釐清後，四個具體抱怨：

1. **剪影只有 2–3 種** —— 一整條街同樣的形狀輪流出現
2. **高樓重複性太高**
3. **非高樓的建築沒有窗戶**
4. **建築上的元素太少**（低樓缺地面元素、高樓缺屋頂裝飾）

明確**不**在抱怨範圍內、因此本設計不動的：建築朝向、色盤。

---

## 2. 目標與非目標

### 目標

- 讓每個分區的建築剪影從 2–3 種增加到視覺上「幾乎不重複」
- 讓所有分區的建築都有立面細節（窗戶／店面／廠房開口）
- 加上裝飾元素：低樓的地面物件、高樓的屋頂物件
- 建築升級（1→2→3 級）時**換成不同建築**，不只是拉高
- 提供一個**展示區**，讓所有調整在進遊戲前就能確認

### 非目標

- 不做屋齡／風化系統（需要真的 tick，是另一個功能，混做會兩件都做不好）
- 不改建築朝向邏輯（目前隨機四向，玩家不介意）
- 不重新設計色盤
- 不改基礎設施建築（電廠、警局等）的模型
- 不動任何遊戲邏輯（生長、升級、廢棄規則全部不變）

---

## 3. 現況分析

### 目前的變化來源

全部由 `hash(x, y)` 決定，因此存檔重開一致：

| 手段 | 現況 | 對剪影的貢獻 |
|---|---|---|
| 幾何變體 | 每分區 2–3 種手寫模型（`VARIANTS`） | **唯一來源** |
| 縮放 | 高度依等級 ±35%、寬深各 ±15% | 只改胖瘦 |
| 旋轉 | 隨機四向 | 不改形狀 |
| 顏色 | 每區 8–12 色盤 + HSL 微抖 | 無 |
| 立面 | shader 程序化生成 | 無 |

`VARIANTS` 共 17 個變體（住宅低 3、住宅高 3、商業低 3、商業高 2、工業 3、辦公 3）。

### 架構限制

每個 (分區, 變體) 是一個 `THREE.InstancedMesh`，**同一變體的所有實例共用同一份幾何**。因此「每棟樓幾何都不同」不可行，變化只能來自三處：

1. 更多變體（成本：draw call + 預配記憶體）
2. 逐實例的矩陣／顏色／自訂屬性
3. shader

現況每個變體預配 `maxPerVariant = 6000` 格，17 個變體約 6.5 MB 常駐。

### 已定位的根因

- **剪影重複** ← 每分區只有 2–3 個幾何
- **高樓重複** ← 除了幾何少，shader 的 `floorH = 0.25`、`winW = 0.2` **寫死**，所有住宅高／辦公的窗戶格完全一致
- **低樓沒窗戶** ← shader 的 `vZoneCat < 0.1` 分支只畫水平壁板線，沒有窗戶格
- **元素太少** ← 幾何裡沒有屋頂物件，地面物件只有少數變體帶了樹與圍籬

### 兩個既有缺陷（本設計順手修）

**(a) 多路亂數的對角線相關性。** 現在靠偏移輸入產生多條流：

```ts
const h  = hash(x, y);
const h2 = hash(x + 100, y + 100);
const h3 = hash(x + 200, y + 200);
```

`hash(x+100, y+100)` 在 (0,0) 的值等於 `hash(x,y)` 在 (100,100) 的值。所以格子 (0,0) 與 (100,100) 的五條流有四條共用同一批數字、只是換了角色。目前 5 條流影響有限；本設計會讓流數增加到十幾條，相關性就會浮現。

**(b) shader 會在屋頂物件上畫窗戶。** 判定條件是「標籤 = `PART_WALL` 且 `|n.y| < 0.3` 且 `y > 0.06`」，所以水塔、冷氣機、天線都會被畫上窗戶。屋頂物件那一層直接踩到這個。

## 4. 設計

### 4.1 展示區（Showcase）

**Vite 第二個進入點**：新增 `showcase.html` + `src/showcase/`，build 時以 `rollupOptions.input` 掛兩個入口；開發時開 `/showcase.html`。**不載入遊戲**：沒有模擬、沒有 worker、沒有 UI 面板。

**核心約束：展示區必須使用正式的那一份。** 同一個 `getBuildingMaterial()`、同一個幾何生成器、同一套種子規則。在展示區調到滿意的東西，進遊戲必須長得一模一樣，否則展示區沒有價值。

**三種檢視模式：**

| 模式 | 用途 |
|---|---|
| 單體 | 轉盤，看零件比例、屋頂、裝飾細節 |
| **街廓** | 8×8 排滿隨機建築 —— 重複感只有群體出現時才浮現，這是調參數時要盯的畫面 |
| 矩陣 | (分區 × 等級 × 變體) 全部排成表格，找出長得太像的組合 |

**控制項**（即時，不重載）：時間滑桿（日夜與窗戶亮燈）、太陽角度（玻璃高光）、重新擲種子、分區／等級篩選、零件著色（debug）、線框與三角形計數。

展示區同時驗證了生成器介面是否乾淨：如果它只靠「給我 (分區, 等級, 種子) 回傳幾何」就能跑起來，介面就是對的。

### 4.2 零件詞彙與參數空間

**分層模型** —— 每棟建築由五層組成：

| 層 | 內容 | 解決 |
|---|---|---|
| 量體 | 主體積的組合方式 | 剪影 |
| 屋頂 | 斜頂／四坡／平頂女兒牆／階梯／鋸齒 | 剪影 |
| 立面附加 | 陽台帶、簷口、壁柱、雨遮、門廊 | 元素太少 |
| 屋頂物件 | 水塔、冷氣機組、天線、樓梯間、尖塔、看板 | 高樓裝飾 |
| 地面物件 | 圍籬、樹、車道／車庫、垃圾桶、停車、花台、貨櫃 | 低樓地面元素 |

**量體語法** —— 九種原型，各帶 3–5 個參數：

| 原型 | 參數 | 用於 |
|---|---|---|
| 單量體 | 寬深比、高度 | 全部 |
| L 形 | 翼長、翼向（4 種） | 住宅低、商業低 |
| 連棟 | 棟數 2–4、各棟寬度微差 | 住宅 |
| 退縮塔 | 退縮次數 1–3、收分比、偏移方向 | 高樓 |
| 雙塔／翼 | 間距、兩塔高差 | 住宅高、辦公 |
| 裙樓＋板樓 | 裙樓覆蓋率、板樓厚度與偏心 | 商業高、辦公 |
| 中庭街廓 | 四翼、中庭大小 | 住宅高 |
| 鋸齒廠房 | 齒數、齒向 | 工業 |
| 圓柱核 | 半徑、與方量體的疊合 | 辦公 3 級（稀有） |

**分配表** —— 決定每個 (分區, 等級) 會長出什麼：

| 分區 | 1 級 | 2 級 | 3 級 |
|---|---|---|---|
| 住宅低 | 小屋＋斜頂、L 形農舍 | 兩層樓房、雙拼 | 3 連棟、帶翼別墅 |
| 住宅高 | 四層步登公寓、轉角切角 | 六八層板樓、中庭街廓 | 退縮塔、雙塔、裙樓＋板樓 |
| 商業低 | 單層店面＋雨遮＋招牌 | 兩層店住 | 小型百貨、轉角騎樓 |
| 商業高 | 裙樓塊體 | 中層＋簷口 | 玻璃退縮塔＋冠部 |
| 工業 | 廠棚＋煙囪 | 鋸齒廠房＋筒倉 | 大型廠區＋冷卻塔＋管架 |
| 辦公 | 低層玻璃盒 | 中層板樓＋核心 | 高退縮塔＋尖塔 |

屋頂走向刻意與等級綁定：住宅低是陶瓦／石板斜頂；住宅高 1–2 級是巴黎鋅板斜頂、3 級才轉平頂加屋頂物件。**光看屋頂就能分辨等級。**

**每桶變體數**：8。搭配下節的連續立面種子，視覺上接近不重複，而 draw call 只有 8。

**新增零件標籤 `PART_DETAIL`**，插在 `PART_WALL`（0.0）與 `PART_FOLIAGE`（0.5）之間的空號段（取 0.2）：金屬／深色、不畫窗戶。屋頂物件與部分地面物件用它。這必須在階段 1 的 shader 改動裡先做掉，否則階段 3 無法進行。

**三角形預算**：低密度住宅 ≤ 400、3 級塔樓（含屋頂物件）≤ 800。展示區的計數器照這兩條線標示。

### 4.3 種子與決定論

```
外觀 = f(x, y, zoneType, level, seedByte)
```

**`seedByte` 是新增的持久化欄位。** 建築生成時擲一個 0–255 的亂數 byte 寫進格子，升級時保留，拆除時清除、重蓋時重擲。

**為什麼是亂數 byte 而不是建立時間：**

- 建商是批次生長的，同一個 growth tick 冒出來的一整片會共用同一個 tick 值，等於沒有隨機
- tick 是遞增序列，相鄰值高度相關，餵進 hash 前還要再混一次
- 亂數 byte 直接是均勻分布、256 種，語意單純

**儲存方式** —— 照 `Grid` 既有的側邊陣列模式：

```ts
private buffer: ArrayBuffer;          // 12 bytes/cell 緊密佈局
readonly reservedData: Uint8Array;    // 這三個已經在外面
readonly railTypeData: Uint8Array;
readonly railFlagsData: Uint8Array;
readonly variantSeedData: Uint8Array; // ← 新增，照抄同一模式
```

因此：

- `BYTES_PER_CELL` 維持 12，`CELL_OFFSET` 不動，`Grid.test.ts` 的佈局測試不用改
- worker 的 buffer 傳輸不受影響
- 渲染層本來就在讀 `cell.reserved`，多讀一個欄位是零成本
- 記憶體：200×200 = 40 KB

**必要的連帶改動：**

- `CellData` / `DEFAULT_CELL` / `CELL_KEYS` 加欄位 —— `EveryFieldIsAccountedFor` 測試會強制 `Serializer` 一起補，忘記就紅燈
- 存檔版本 bump + 遷移
- **遷移時要幫舊存檔的每一棟既有建築擲一次種子**，否則舊城市全部是 0 號樣式，玩家看不到成果
- core 的唯一改動：`BuildingGrowth` 在建築生成時擲 byte 寫入格子

**行為表：**

| 事件 | seedByte | 外觀 |
|---|---|---|
| 存檔重開 | 讀回 | 完全一樣 |
| 升級 1→2→3 | 保留 | 換一棟，同一塊地保有延續性 |
| 重劃分區 | 重擲（重劃會拆除既有建築） | 換一棟 |
| 拆掉重蓋 | 重擲 | 不一樣 |
| 舊存檔載入 | 遷移時擲 | 立即散開 |

**修掉多路亂數的相關性**：改用把流編號混進雜湊的 `hash3(x, y, stream)`，取代現行的偏移輸入寫法。階段 1 就換掉，之後所有新流才有乾淨來源。

### 4.4 shader 介面

新增逐實例屬性 `aSeed`（`vec3`，三條獨立流）：

| 分量 | 控制 | 現況 |
|---|---|---|
| `x` | 樓層高度 0.22–0.30、窗寬 0.16–0.24 | 寫死 `floorH = 0.25`、`winW = 0.2` |
| `y` | 立面節奏相位、有無簷口／分帶 | 沒有 |
| `z` | 屋頂色與立面材質偏好（玻璃⇄粉刷比例） | 由世界座標 hash 決定 |

**窗戶對齊**：窗戶格目前算在世界座標上（`wallU = vWorldPos.x` 或 `.z`），好處是尺寸不隨建築縮放變形，這點保留。壞處是整張地圖共用同一個網格，相鄰建築的窗戶橫向對齊，看起來像機器印的。解法是用 `aSeed.y` 給每棟一個**相位偏移** —— 尺度仍是真實尺度，但起算點不同。不改用局部座標，那會讓窗戶隨縮放拉長。

**低密度住宅的立面**：`vZoneCat < 0.1` 分支從「只有壁板線」擴充為帶窗戶、門、（可選）陽台的立面，比例由 `aSeed` 決定。

**新增 `PART_DETAIL` 分支**：在牆面分支之前判斷，走金屬／深色路徑，不畫窗戶。

現有的 `aHighlight` / `aHighlightColor` / `aOccupancy` 不動。

### 4.5 模組拆分

`BuildingRenderer.ts` 目前 3670 行（幾何 builder、shader、實例管理混在一起），階段 2、3 會再加 2000+ 行。照專案既有的 `src/renderer/geometry/`（車輛零件已是此模式）拆：

```
src/renderer/geometry/buildings/
  parts.ts        零件標籤（含 PART_DETAIL）、合併工具
  massing.ts      九種量體原型
  roofs.ts        屋頂
  facade.ts       陽台帶、簷口、雨遮、門廊
  roofProps.ts    水塔、冷氣機、天線、尖塔
  groundProps.ts  圍籬、樹、車庫、貨櫃
  registry.ts     (分區, 等級) → 生成器；三角形預算
src/renderer/
  BuildingMaterial.ts    shader 原始碼 + material singleton
  BuildingAppearance.ts  hash3、流編號、appearanceOf(x, y, zone, level, seed)
  BuildingRenderer.ts    只剩實例管理：add/remove/update、容量、occupancy、highlight
```

`BuildingAppearance.ts` 是純函式、不 import Three.js，展示區與遊戲共用，也最容易測。

### 4.6 容量配置與 LOD

變體從 17 個增加到 6 分區 × 3 等級 × 8 = **144 個**。若維持每個預配 6000 格，常駐記憶體會膨脹到 50 MB 以上。

改為**動態成長**：初始容量小（例如 256），滿了就重配為兩倍並複製既有實例資料。實例矩陣、顏色與所有自訂屬性都要一起搬 —— 這是本設計最容易寫出索引 bug 的地方，測試要涵蓋（見 §6）。

**LOD**：因為屋頂物件與地面物件是獨立的 InstancedMesh 層，遠距離時把該層 `count` 設 0 即可，主體量體不動。不需要真正的 LOD 幾何。

## 5. 階段規劃

每一階段都在展示區調到滿意才進下一階段，最後才一次接進遊戲。

| 階段 | 內容 | 解決 |
|---|---|---|
| **0** | 抽出幾何生成介面 + 展示區骨架（先接現有 17 個變體，確認展示區可用）；量一個大城 frame time 基準 | 基礎建設 |
| **1** | `hash3` 換掉偏移雜湊；`aSeed` 屬性；`PART_DETAIL`；各分區立面（含低密度住宅窗戶） | 「非高樓沒有窗戶」「高樓重複」 |
| **2** | 參數化生成器；`VARIANTS` key 改成 (分區, 等級)；容量動態配置 | 「剪影只有 2–3 種」「高樓重複」 |
| **3** | 裝飾物層（屋頂物件、地面物件） | 「元素太少」 |
| **4** | `seedByte`：Grid 側邊陣列、`BuildingGrowth` 擲值、Serializer、遷移；LOD；接進遊戲驗收 | 「拆掉重蓋要不一樣」 |

階段 1 可獨立出貨，馬上看得到差別；階段 2 是最大的一塊。

## 6. 測試策略

### 寫測試的部分

| 對象 | 測什麼 | 防什麼 |
|---|---|---|
| 幾何生成器 | 三角形數在預算內 | 不知不覺加重 |
| 幾何生成器 | 包圍盒不超出格子 | 翼、雨遮、樹伸進鄰格或馬路 |
| 幾何生成器 | 每個頂點都有零件標籤 | 漏標的面被當牆畫窗戶 |
| 幾何生成器 | 同種子 → 完全相同的頂點緩衝 | 決定論 |
| `appearanceOf` | 五個輸入以外無其他依賴 | 存檔重開不一致 |
| `appearanceOf` | 各條流互相獨立 | §3(a) 的對角線相關性 |
| `appearanceOf` | 變體分布大致均勻 | 某個變體幾乎不出現 |
| 實例管理 | 隨機 add/remove N 次後，每個位置對應的矩陣仍正確 | swap-with-last 索引 bug（桶從 17 增到 144） |
| 容量成長 | 重配後所有既有實例的矩陣、顏色、自訂屬性都正確 | §4.6 的搬移遺漏 |
| 存檔 | `seedByte` 往返；舊檔遷移後不是全 0 | |

所有測試遵循專案的 TDD 規範：先寫紅燈測試，修好後還原修正確認轉紅。

### 測不了的部分

GLSL 本身無法單元測試。shader 只能測介面契約（`aSeed` 屬性存在、`itemSize` 正確、`setInstanceData` 有寫入）。**外觀正確與否由人在展示區以眼睛驗收** —— 這是展示區存在的理由。

---

## 7. 驗收條件

接進遊戲前必須全部滿足：

1. 展示區街廓模式（8×8，同分區同等級）中，相鄰兩棟外觀完全相同的比例 **低於 5%**
2. 三角形預算：低密度住宅 ≤ 400、3 級塔樓 ≤ 800
3. 大城（200×200 蓋滿）frame time **不比階段 0 量到的基準差**
4. 現有 4230 個測試全綠，`tsc --noEmit` 零錯誤，`pnpm build` 可產出
5. 存檔往返正確；舊存檔載入不報錯、不損毀，且建築外觀已散開

## 8. 風險與已知取捨

| 風險 | 處置 |
|---|---|
| 144 個 InstancedMesh 的 draw call | 玩家已選擇「好看優先」；若實測有問題，用 LOD 與合併稀有變體處理 |
| 容量動態成長的索引 bug | 這是本設計最危險的一塊，測試已列為必要項 |
| 存檔版本 bump 影響既有城市 | 遷移時擲種子；`EveryFieldIsAccountedFor` 與既有的載入失敗處理（隔離、明確報錯）已在上一輪建立 |
