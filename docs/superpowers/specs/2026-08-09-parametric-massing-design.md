# 階段 2C-1：參數化量體生成器

**目標**：把手寫的 2–3 個變體換成每桶 8 個由參數生成的變體，並取消實例縮放，
讓「一條街上每棟都很像」與「形狀本身太素」這兩件事同時改善。

**前置**：階段 2A（高度／寬度表）、2B（地面物件層）、2B-2（三類放置帶）已完成。

**不在本階段**：屋頂物件、立面附加零件、地面詞彙擴充（全部在 2C-2，詞彙清單見
附錄）；LOD 與遠距離簡化（階段 4）。

---

## 一、現況量測

這份規格的每一個決定都來自下面這三組數字，不是猜的。

### 相鄰重複率

在 24×24 的街廓上，用現行的逐格雜湊分配變體：

| 分區 | 變體數 | 相鄰同變體 | 相鄰同面貌 |
|---|---|---|---|
| 住宅低／住宅高／商業低／工業／辦公 | 3 | **33.4%** | 8.5% |
| 商業高 | 2 | **49.9%** | 12.1% |

**「同面貌」8.5% 是假的安慰。** 那個數字把「同變體但旋轉 90°」算作不同，但現行
變體幾乎都是置中的方盒子加一頂蓋 —— 轉 90° 在視覺上是無操作。玩家看到的是
33%（商業高 50%）。

**推論一：旋轉只有在形狀不對稱時才有價值。** 生成器必須刻意產出不對稱的變體，
否則加再多變體也只是把同一個盒子換個尺寸。

### 等級對外型毫無影響

```ts
export function getVariants(zoneType: number, level: number): GeoBuilder[] {
  void level;                       // ← 就是這一行
  return VARIANTS[zoneType] ?? [];
}
```

L1 到 L3 用同樣三個形狀，只有整體 Y 縮放不同。規格修訂 4 說的「等級的豪華階梯」
在量體上根本不存在，目前完全靠貼片／矮物件／懸挑三層在撐。

### 三角形預算用不到一成

| 分區 | 量體 | 貼片 | 矮物件 | 懸挑 |
|---|---|---|---|---|
| 住宅低 L3 | 48 | 10 | 188 | 0 |
| 商業低 L3 | 24 | 10 | 208 | 12 |
| 工業 L3 | 72 | 30 | 248 | 8 |

預算是 HOUSE 400／TOWER 800。**量體是三角形用得最少的一層，卻是視覺上最重要的
那一層。** 腳下的小東西比建築本身多三到五倍。

### draw call 基準

```
zoneLayer 60 ｜ decalLayer 21 ｜ propLayer 48 ｜ overheadLayer 18 ｜ 合計 147
```

## 二、核心決定：取消實例縮放

現在每一棟的實例矩陣是：

```
scale( footprint(width01), heightScaleFor × heightScale, footprint(depth01) ) × rotation
              ±15%                ±10%                        ±15%
```

**這個縮放是這個子系統所有已知缺陷的共同來源。** BUG-219（升級把庭院的樹拉高
1.75 倍）、BUG-226（雨遮貼著一棟沒人看得到的假想建築）都是它 —— 附掛層的幾何是
整個桶共用的一份，而量體會抖，附掛層看不到它抖多少。

生成器既然要重寫，就讓它**直接產出最終尺寸的幾何**：

```
現在   目標高度 × heightScaleFor × (1 ± 10%)     ← 拉伸同一個形狀
改後   樓層數 × 樓高                              ← 這一棟就是多兩層
```

高度變化從「同一個形狀被拉長」變成「八個變體本來就是不同樓層數」。那不只是實作
上比較乾淨，觀感也比較對：高的那一棟看起來高，是因為它真的多了兩層樓。

**連鎖效果：**

- 實例矩陣退化成**旋轉 + 位移**，與三個附掛層完全一致
- `narrowestBuildingEdge` / `widestBuildingEdge` 從「目標寬乘抖動係數」變成
  「量這一桶所有變體的實際最小／最大值」—— 是量出來的，不是推出來的
- 屋頂物件變得可行（2C-2）：沒有 Y 縮放就沒有 BUG-219

**代價：** 高度不再連續，而是八個離散值。這其實是改善 —— 一條街上八種樓層數
讀起來像規劃過的，連續抖動讀起來像雜訊。

## 三、中間表示：`Volume`

生成器不直接產出 `BufferGeometry`，而是先產出一串盒子的座標：

```ts
/** 一個軸對齊的量體。座標是格（1 格 = 12 m），y0 = 0 是地面。 */
export interface Volume {
  x: number; z: number;   // 中心
  w: number; d: number;   // 寬深
  y0: number; y1: number; // 底與頂
}
```

原型是 `(dims: Dimensions, rng: Rng) => Volume[]`，純算術，不 import Three.js。

**為什麼值得多一層：**

1. 「L 形有沒有真的不對稱」「兩翼有沒有重疊」「有沒有越過行人包絡線」全部可以
   用算術精確驗證，不必量合併後的包圍盒。階段 2B 的 BUG-222 正是因為只能量
   包圍盒而漏掉「離格心最大距離」與「包圍盒寬度」的差別。
2. `propBands` 可以直接讀 `Volume` 算出這一桶的最窄／最寬牆面，不必先把八個
   變體的幾何都建出來。

## 四、模組結構

```
src/renderer/geometry/buildings/massing/
  metrics.ts     共用純量常數
  rng.ts         variantRng(zone, density, level, variantIndex)
  dimensions.ts  這個變體的基地寬深與樓層數
  prototypes.ts  各分區的量體原型 → Volume[]
  roofForms.ts   屋頂形式 → Volume[] 或幾何
  assemble.ts    Volume[] → BufferGeometry（貼標籤、置中、驗證）
  index.ts       getMassingVariants(zone, density, level): GeoBuilder[]
```

### `metrics.ts` 存在的理由

`propBands` 要量 `massing` 的變體，而 `massing` 要用 `SHOPFRONT_CEILING` ——
這是一個循環。把兩邊都要的純量常數搬到葉節點模組就沒事了：

```ts
export const HALF_ENVELOPE      // 行人包絡線半寬 0.40833
export const CELL_EDGE = 0.5
export const FLOOR_HEIGHT_UNITS = { MIN: 0.22, MAX: 0.30 }
export const SHOPFRONT_CEILING = FLOOR_HEIGHT_UNITS.MIN
export const OVERHEAD_CLEARANCE
export const GROUND_LAYERS
```

`propBands.ts` 因此收乾淨成「只管三類放置帶」。

### 各模組的責任

| 模組 | 輸入 | 輸出 | 依賴 |
|---|---|---|---|
| `rng` | (分區, 密度, 等級, 變體序號) | `() => number` 0..1 | 無 |
| `dimensions` | 同上 | `{ w, d, floors, floorHeight }` | `metrics`、高度／寬度表 |
| `prototypes` | `Dimensions`、`Rng` | `Volume[]` | `metrics` |
| `roofForms` | 頂部 `Volume`、`Rng` | `Volume[]` | `metrics` |
| `assemble` | `Volume[]` | `BufferGeometry` | Three.js、`parts` |
| `index` | (分區, 密度, 等級) | `GeoBuilder[]` | 以上全部 |

只有 `assemble` 碰 Three.js。其餘四個是純算術，測試不需要幾何。

## 五、尺寸推導

### 變體數固定為八

`V = 8`，所有 (分區, 密度, 等級) 一致。八是「相鄰重複率」與「桶數」的折衷：
純逐格雜湊的重複率是 `1/V`，八個是 12.5%，配上第九節的鄰居迴避才壓得到 5% 以下；
再往上加變體只會線性推高 draw call。

### 樓層數分層鋪滿

目標高度來自既有的 `TARGET_HEIGHTS_M[分區:密度][等級]`。八個變體的高度**分層
鋪滿** ±10%，而不是隨機取樣 —— 隨機取樣有可能八個都擠在中間：

```
h(vi) = target × (0.9 + 0.2 × (vi + 0.5) / V)
floors = max(1, round(h(vi) / floorHeight))
實際高度 = floors × floorHeight
```

`floorHeight` 由 `rng` 在 `FLOOR_HEIGHT_UNITS` 的範圍內取，**每個變體一個值**
（不是每一格一個值）。

### 基地寬深

目標寬度來自既有的 `TARGET_WIDTHS_M`。每個變體的 `w`、`d` 各自在
`[0.85, 1.0] × 目標` 內取，且必須滿足 `maxAbs ≤ HALF_ENVELOPE`。

**上限是硬的**：越過行人包絡線就是行人穿牆（BUG-221）。`assemble` 會檢查並在
違反時丟例外 —— 生成器的錯誤要在建構時就炸掉，不是在畫面上默默出現。

例外在**遊戲執行時不該發生**：生成器是確定性的，變體集合固定，所以測試跑過就
表示永遠不會丟。那個 `throw` 是給未來改原型的人的護欄，不是執行期的錯誤處理。

八個變體如何對應到四到五個原型：`variantIndex` 依序輪流取（`vi % 可用原型數`），
所以每個原型至少出現一次，多出來的名額由 `rng` 給不同尺寸。

**L1 是最難的一格。** 住宅低 L1 只有兩個原型可用，八個變體要靠尺寸變化撐出差異；
住宅高 L3 有五個原型，輕鬆得多。所以「兩兩變體輪廓不同」這條測試要逐桶跑，
**L1 過了才算過** —— 它才是會退化的那一格。若 L1 撐不住，補救是替低等級再加一個
簡單原型（例如住宅低的「單體 + 前院凸窗」），而不是放寬測試。

### 不對稱配額

**每桶至少 6/8 的變體，旋轉 90° 後輪廓必須改變。** 這是驗收條件，不是建議 ——
旋轉是四倍的免費變化，但只有在形狀不對稱時才拿得到。

## 七、屋頂形式

屋頂形式與原型分開挑，所以「L 形 + 山牆」與「L 形 + 平頂女兒牆」是兩個變體。

| 形式 | 適用 | 說明 |
|---|---|---|
| 山牆 | 住宅低 | 四角錐壓扁，沿長邊 |
| 四坡 | 住宅低 | 金字塔 |
| 平頂 + 女兒牆 | 住宅高、商業、辦公 | 頂面內縮，圍一圈矮牆 |
| 平頂 + 頂冠 | 商業高、辦公（L3） | 頂部再收一段 |
| 鋸齒 | 工業 | 三到四道斜面，朝同一方向 |
| 單斜 | 工業、商業低 | 一面斜 |

`roofForms` 只回傳 `Volume[]`（或斜面的四點），**不放任何設備** —— 水塔、空調、
煙囪是 2C-2 的詞彙。

## 八、窗戶對齊真正的樓板線

量體既然量化到整層，就讓立面 shader 畫的窗戶橫列對齊真正的樓板：

```
現在   aSeed.x ← 逐格雜湊（每一格自己一個樓層節奏，與幾何無關）
改後   aSeed.x ← 由變體決定（與這個變體幾何的 floorHeight 相同）
```

`BuildingRenderer.setInstanceData` 從 `app.facadeSeed[0]` 改成讀變體的
`floorHeight`，反解回 0..1。

**副作用（有意的）**：`floorHeight` 在 shader 裡同時驅動窗寬與立面材質，所以同一
變體的所有實例會共用窗戶節奏。那是對的 —— 同一個設計的建築本來就長一樣，變化
應該來自變體本身。

**這一項可以單獨拿掉**，不影響其他任何部分。留著的理由是「形狀太素」有一大塊
其實是窗格與樓板各畫各的。

## 九、鄰居迴避

純逐格雜湊的相鄰重複率就是 `1/V`：八個變體 = 12.5%。要靠變體數壓到 5% 以下得
寫二十個變體。

```ts
// BuildingAppearance.ts
export function variantIndexFor(x, y, seedByte, n): number {
  const raw = (px: number, py: number) =>
    Math.floor(hashCell(px, py, seedByte, STREAM.VARIANT) * n) % n;
  const v = raw(x, y);
  const banned = new Set([raw(x - 1, y), raw(x, y - 1)]);
  if (!banned.has(v)) return v;
  // 從「兩個鄰居都沒用」的值裡挑，而不是 +1 位移 —— 位移過去有可能正好
  // 撞上另一個鄰居。
  const allowed: number[] = [];
  for (let k = 0; k < n; k++) if (!banned.has(k)) allowed.push(k);
  const r = hashCell(x, y, seedByte, STREAM.VARIANT_RETRY);
  return allowed[Math.floor(r * allowed.length) % allowed.length]!;
}
```

O(1)、確定性、不需要知道鄰居的最終值。

**這是降低而不是消除。** 比對的是鄰居的**原始**雜湊值，而鄰居自己也可能被換過，
換完之後仍可能撞上。期望值：

    P(西鄰被換過)        ≈ 2/8 = 25%
    P(換完之後等於我)     ≈ 1/7 ≈ 14%
    P(最終相鄰同變體)     ≈ 0.25 × 0.14 ≈ 3.5%

低於 5% 的驗收線，但餘裕不大。實作時要實測並記錄真實數字；若量到的高於 5%，
補救順序是：先比對兩層鄰居（西、北、西北），再考慮加變體數。兩者都不改變架構。

## 十、效能

```
量體桶  60 → 168（7 個「分區:密度」 × 3 等級 × 8 變體）
```

three.js 對 `count === 0` 的 `InstancedMesh` 仍會送出 draw call。桶數三倍之後
這件事從「無所謂」變「有感」，所以 `InstancedLayer` 在 `acquire` / `release` /
`reset` 時同步維護：

```ts
mesh.visible = count > 0;
```

一行，救的是遊戲開局與稀疏城市 —— 成熟城市裡多數桶是滿的。

**記憶體**：168 桶 × 256 初始容量 × 約 108 B（矩陣 + 顏色 + 四個屬性）≈ 4.6 MB。
可接受。

## 十二、測試策略

### 不碰 Three.js 的（`Volume` 層）

| 測試 | 擋住什麼 |
|---|---|
| 原型的量體互不重疊 | 兩翼疊在一起會產生內部面，畫面上看不出來但白吃三角形 |
| 每個量體都在行人包絡線內 | BUG-221：行人穿牆 |
| 高度等於「樓層數 × 樓高」 | 高度回到連續拉伸 |
| 八個變體的高度覆蓋 ±10% 全範圍 | 八個都擠在中間 |
| 兩兩變體的輪廓不同 | 生成器退化成只產一種 |
| ≥ 6/8 的變體旋轉 90° 後輪廓改變 | 旋轉變回視覺無操作 |
| L3 可用原型 ⊇ L1 可用原型 | 等級階梯消失 |

**輪廓比對**：把 `Volume[]` 光柵化成 16×16 的佔用格，格值 = 該格的最高點（沒有
量體的格是 0）。兩個輪廓的差異率定義為

    差異率 = |{ 格 : |a[格] − b[格]| > 樓高的一半 }| ÷ 256

- 「旋轉有意義」：把自己旋轉 90° 之後，差異率 ≥ **0.10**
- 「兩個變體不同」：兩者的差異率 ≥ **0.10**

門檻寫死在測試裡而不是憑感覺 —— 光柵化本身就是為了讓「看起來不一樣」變成一個
算得出來的數字。

### 碰 Three.js 的（幾何層）

| 測試 | 擋住什麼 |
|---|---|
| 同樣的 (分區, 密度, 等級, 變體序號) 產出逐頂點相同的幾何 | 亂數洩漏，存檔前後長不一樣 |
| 底面在 y = 0、XZ 置中 | BUG-222 的置中前提 |
| `maxAbs ≤ HALF_ENVELOPE` | 同上，直接檢查而不是透過縮放公式 |
| 三角形數在預算內，且 L3 > L1 | 規格修訂 4 |
| 每個頂點都有零件標籤，且沒有 `PART_GROUND` | 量體長出鋪面顏色 |

### 整合層

| 測試 | 擋住什麼 |
|---|---|
| 64×64 街廓的相鄰同變體率 < 5%（每分區每等級） | 本階段的主要驗收條件 |
| 量體層的實例矩陣縮放為單位矩陣 | 縮放偷偷回來 |
| 空桶 `visible === false`，非空桶 `true` | draw call 白花 |

### 回退驗證

每一條新測試都要做回退驗證：把修正暫時拿掉，確認測試轉紅。**階段 2B-2 的
BUG-226 正是因為測試量錯了對象而給了假綠燈** —— 一條沒被驗證過會轉紅的測試
等於沒有。

---

## 十三、驗收標準

1. 相鄰同變體率 **< 5%**（64×64，每分區每等級）
2. 每桶 ≥ 8 個變體，兩兩輪廓不同
3. ≥ 6/8 的變體旋轉 90° 後輪廓改變
4. 量體層的實例矩陣**不含任何縮放**
5. 每棟高度 = 該等級目標高度的 ±10% 內，且八個變體覆蓋整個範圍
6. 沒有變體越過行人包絡線
7. L3 的三角形數 > L1，且都在預算內
8. 全量測試綠、`tsc` 0 錯、`pnpm build` 成功
9. 使用者在展示區確認街廓不再有「每三棟就一棟一樣」的感覺

## 實作後的修正（2026-08-09）

實作途中有三處與本規格不同的決定，都在計畫裡標明並附了理由。記在這裡，
免得下一個讀規格的人照著錯的數字做。

### 一、高度容差改成 `max(10% × 目標, 一層樓)`

第五節與第十三節寫的是固定 ±10%。**那是錯的模型。**

高度必須是整數層乘樓高，而樓高只能落在 [2.64, 3.6] m。對矮建築來說一層樓
就是目標的一大截：

    住宅低 L1，目標 5 m，±10% = [4.5, 5.5]
      1 層 × [2.64, 3.60] = [2.64, 3.60]   全部太矮
      2 層 × [2.64, 3.60] = [5.28, 7.20]   只有 5.28 落得進去
                                            → 一個選項，八個變體高度全一樣

而 42 m 的塔樓多一層才多 8%，百分比才咬得住。

「至少容得下一層樓」是這條規則的全部理由：**低於一層樓的容差在整數層的世界裡
沒有意義**。

**等級階梯因此改成看平均值。** 住宅低 L1 [3.8, 8.8] 與 L3 [8.8, 12.8] 會重疊
—— 一棟三層的 L1 可能比一棟兩層的 L3 高。這是刻意接受的：低矮住宅的等級差異
本來就寫在裝潢與院子上，而「有時候一層有時候三層」正是郊區街道真正的樣子。
高樓那一端百分比先咬到，所以住宅高的三個等級區間仍完全不重疊
（20.2–24.3 / 28.8–35.0 / 39.6–45.5）。

### 二、不對稱配額從 6/8 降到 4/8

第六節寫「每桶至少 6/8 的變體旋轉 90° 後輪廓必須改變」。**高樓做不到** ——
板樓與裙樓塔本質上是對稱的，而它們是高密度分區在 L1 僅有的原型。硬湊 6/8
只會逼出不合理的形狀。

主要條件改成「**八個變體的輪廓兩兩相異**」（實測每桶 28/28 對），不對稱降為
4/8（實測 4–6/8）。

**排原型表時因此多了一條約束：不對稱的排前面。** `prototypeFor` 用
`variantIndex % 可用原型數` 輪流取，而 8 通常不是原型數的倍數 —— 繞回來的那
幾個一定落在清單開頭。對稱的排前面時，住宅高 L2（六個原型）只湊得出 3/8。

### 三、拿掉「一樓凹進（騎樓）」原型

它在俯視高度圖裡看不出來 —— `rasterise` 取的是最高點，凹進去的一樓被上面的
樓層蓋住，所以它會與「單一量體」判定成同一個輪廓，讓「八個變體兩兩相異」
那條測試失效。

騎樓的視覺效果本來就由懸挑層的雨遮負責（階段 2B-2）。
